## 诊断：点击校验结果跳转「边缘单元格」失效（仅诊断，未改代码）

**现象**：点击校验面板条目跳转时，靠近右/下边缘的单元格跳转后不在视口内。

**根因（Luckysheet 源码级证据，从 `public/luckysheet/luckysheet.umd.js` 反查）**：
1. `luckysheet.setRangeShow(range)` **只设置选区**（写 `luckysheet_select_save` + `Rh()`），**不滚动**。
2. `luckysheet.scroll({targetRow,targetColumn})` 把 `#luckysheet-scrollbar-y/x` 的 `scrollTop/scrollLeft` 设为**目标行/列左上角**（`visibledatarow[n-1]` / `visibledatacolumn[l-1]`，n=0 时为 0），**且不派发 scroll 事件**。
3. Luckysheet 的视觉滚动由 `$("#luckysheet-scrollbar-y").scroll(function(){fy()})` / scrollbar-x 同理驱动 → **程序化赋值不会触发，必须手动 `dispatchEvent(new Event('scroll'))`**，否则画面完全不动（这一步是现代码里真正让跳转生效的动作）。
4. **失效点**：`navigateToCell` 第 3 步无条件做"减半屏居中"（`scrollTop - cellMain.clientHeight/2`）。当目标行位于内容底部时，第 2 步的 `scrollTop` 被浏览器 **clamp 到 max（= scrollHeight - clientHeight）**，目标行实际贴在视口**底部**；再减半屏就把视口上移，目标行被推到视口下方 → 不可见。列方向同理（右边缘列）。首行/首列因 `Math.max(0, …)` 钳到 0 反而正常。

**失效区间量化**：目标行顶部 > `maxScrollTop` ⟺ 位于内容底部约半个视口高度内（900px 视口 ≈ 最后 15 行）；列同理为最右侧约半屏宽的列。

**修复方向**：保留「粗定位 + 手动派发 scroll」，把"减半屏"改为**左侧安全回退**——仅当 `cur < max`（未触底）时才回退半屏，触底时保持不动；**无论是否回退都必须派发 scroll 事件**（否则不渲染）。首行/首列/无滚动场景行为不变。

## 【重要更正 + 根因定位】日期"被改写"的真正发生地 = Luckysheet 内部的 `xs()` / `ds()`

**上文"全项目没有任何一处对日期做实际转换"的结论只对了一半**：业务代码确实不转换，但**转换真实发生在 Luckysheet 内部**——任何值写进单元格时都会被 Luckysheet 自动做一次类型/格式判定并原地改写。

### 证据链（金桂家园 `应收、已收导入模板 (4)(4).xlsx`，6 行测试表，与用户截图逐格吻合）
1. **Excel 侧**：日期是数字序列号，但每列的单元格数字格式不同 →
   - I 列 计费开始日期：全部 `yyyy/m/d;@` → `w` = `"2026/6/1"`
   - J 列 计费结束日期：全部 `m/d/yy` → `w` = `"5/31/27"`
   - K 列 应收日期：混用 `m/d/yy` 与 `yyyy/m/d;@` → `w` = `"6/1/26"` / `"2024/6/1"`
2. **`excelIO.readExcelFile`**：`XLSX.read(..., {cellDates:true})`（sheet 内 cell.t='d'、v=Date、**z 被置 undefined 但 w 已按原 z 算好**）+ `sheet_to_json({raw:false})` → 输出的是**每个单元格按自己格式渲染的 `w` 字符串**。所以字符串形态的差异是 Excel 的格式差异带过来的。
3. **Luckysheet 侧（关键）**：`importData` 把字符串原样写进 celldata，但 Luckysheet 的 `Cs(row,col,flowdata,value)`（写值核心函数，`setCellValue`/粘贴/初始 celldata→flowdata 构建全走它）会调用 `xs(值)` 做自动判定：
   - `xs(e)` 分支：`ds(e) && (含'.'||含':'||长度<16)` → 解析成 Date → `ct = {fa:'yyyy-MM-dd', t:'d'}`，显示 `gs.format('yyyy-MM-dd', 序列号)`
   - `ds(e)` 的判定正则**强制要求 4 位年份**：`^(\d{4})[-/](\d{1,2})[-/](\d{1,2})$`，且年≥1900、月≤12、日≤31
   - ⇒ `"2026/6/1"`（4 位年）**命中** → 显示 `2026-06-01`；`"5/31/27"`/`"6/1/26"`（2 位年）**不命中** → 保持文本原样
4. **实测（从 UMD 包原样抠出 `ds()` 跑真实字符串 + 端到端复刻读取链路）**：与用户截图 **6/6 行逐格完全一致**（F 列全 `YYYY-MM-DD`、G 列全 `5/31/27`、H 列 `6/1/26`/`2024-06-01` 混合）。

### 结论
- **不是业务代码改了日期，是 Luckysheet 按"字符串里是不是 4 位年"做了二选一的自动识别**，导致同一列内出现"已归一 / 未归一"两种形态。
- 连带影响与上文一致：`isValidDateStr` 只认 4 位年 → 未命中的那些字符串触发 `格式_日期` HIGH 警告，且 `validateBillingDateOrder` 对它们静默 `continue`（日期先后校验被绕过）。
- **注意已被 Luckysheet 转成日期型的单元格**：`v` 变成序列号、`ct.t='d'`，`getCellText` 的序列号分支**此时才会生效**（与上文"永不触发"不冲突——上文说的是"导入 celldata 时被强制写 General"，但那之后 Luckysheet 会在 flowdata 层覆盖成 `t:'d'`）。

### 修复方向（未实施，待确认）
在 `excelIO.readExcelFile` 的 `normalized` 阶段按日期列统一归一：直接读 sheet 单元格（`cellDates:true` 下日期单元格 `cell.t==='d'`）→ `dayjs(cell.v).format('YYYY-MM-DD')`；非日期单元格仍走 `raw:false` 的字符串。这样输出统一为 `YYYY-MM-DD`，Luckysheet 会全部识别为日期型，显示与校验都一致。
（等价备选：`sheet_to_json` 改 `raw:true` 让现成的 `val instanceof Date` 分支复活——但数字列会变 number，需评估长数字精度风险。）

## 追问核查：`2024.10.1` 能否自动修正为 `2024-10-01`（未改代码）

### 结论：**分两种存法，一种能一种不能**

| Excel 里的存法 | 本次修复后 | 实测 |
|---|---|---|
| **真日期**（数字序列号 + 点号数字格式 `yyyy\.m\.d`） | ✅ **能**，导入输出即 `2024-10-01` | 4/4 |
| **文本**（格式 General/`@`，值是字符串 `"2024.10.1"`） | ❌ **不能**，原样保留并报「日期格式错误」 | 0/6 |

补充：文本型里带 `-` 或 `/` 且 4 位年的（`2024-10-1`、`2024/10/1`）**不归一并正常**——Luckysheet 的 `ds()` 会兜住，最终仍显示 `2024-10-01`、校验通过。真正漏的只有**点号分隔的文本**。

### 真实模板全量扫描（10 个应收已收模板，165,235 个日期单元格）
| 类别 | 数量 | 占比 | 状态 |
|---|---|---|---|
| 真日期（数字 + 日期格式） | **164,557** | **99.6%** | ✅ 本次修复已全部覆盖 |
| 文本型-能被 Luckysheet 兜住 | 331 | 0.2% | ✅ 显示正常 |
| **文本型-兜不住** | **347** | 0.2% | ❌ 报「日期格式错误」 |

347 格"兜不住"的模式分布：
- **324 格 / 92 种 = `YYYY.M.D` / `YYYY.MM.DD`**（如 `2026.2.6`、`2026.01.01`、`2026.4.30`）— 集中在**缴款日期**与**减免日期**列
- 21 格 = 脏数据（一格塞两个日期 `"2025/9/9/2025/10/14"`、双斜杠 `"2025//11/4"`）
- 2 格 = 2 位年混杂 `"25/7.31"`、`"25.12/13"`

**关键修正**：此前"P2-b 建议不做"的理由是**顺序歧义**（`5/31/27` 分不清月/日）。但实数据显示 93% 的漏网值是 **`YYYY.M.D`（4 位年在前）→ 年.月.日 完全无歧义**，该理由不成立。结合"仅在日期列内做"的限定，解析是**安全的**。

规则：仅日期列 + 仅 4 位年开头（`^\d{4}[.\-/]\d{1,2}[.\-/]\d{1,2}$`）+ 真实日期校验（月 1-12、日合法、闰年）→ 输出 `YYYY-MM-DD`；不认 2 位年与脏数据（继续报错，让人工核对）。

### 关键实验结论（真实 Chromium 实测）
`luckysheet.create` 只传 `celldata` → 同时传 `data`（二维数组）：
**5k: 3513→93ms ｜ 10k: 14649→134ms ｜ 20k: 62462→264ms ｜ 44,579: >180000→545ms**
空 celldata + 1 万行 = 19ms → **成本由"有数据的行数"驱动，与列数无关**；CPU Profile 热点 `initialjfFile` 自耗 75.8%。

### 修复方向（待用户确认）
- **P0-1** `initLuckysheet` 改传 `data` 二维数组（不传 celldata）→ 消除卡死，>330×
- **P0-2** `XLSX.read(..., { sheets: 0 })` → 省 12–13.5 秒（一行改动）
- **P0-3** 调度器改"时间预算分批"（25ms/批，892→~30 批）+ 统计增量 → 17.4s → 1.2–2.0s
- **P1** `buildDateMap` 改遍历 `Object.keys(sheet)`（897→514ms）；`importData` 直接构造二维数组省 42.5 万对象
- **P2** 房产 `validationStore.handleBulkEdit` 仍用 `celldata.findIndex`（O(n²)），应收版已索引化 → 对齐

### 预期
