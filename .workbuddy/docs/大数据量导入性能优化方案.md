## 三、根因定位

### 根因 1（头号）：Luckysheet `buildGridData` 只吃 `celldata` 时是 O(行数²)

`public/luckysheet/luckysheet.umd.js` 中：

```js
buildGridData: function (e) {
  var r = e.data && e.data.length > 0 ? e.data : Zo([], t, a),   // 只给 celldata 时 → 从空表开始
      n = e.celldata;
  if (e.data && e.data.length > 0) {
    // 线性分支：逐格写入
    for (var l = 0; l < r.length; l++) for (var i = 0; i < r[0].length; i++) Cs(l, i, r, r[l][i]);
  } else if (n && n.length > 0) {
    for (var o = 0; o < n.length; o++) {
      var s = n[o], c = s.r, u = s.c;
      c >= r.length    && (r = Zo(r, c - r.length + 1, 0)),   // ← 每遇到新行号，复制整张已建好的表
      u >= r[0].length && (r = Zo(r, 0, u - r[0].length + 1)), // ← 每遇到新列号，同样复制整表
      ...
```

而 `Zo` 的复制代价是整表：

```js
function Zo(e, t, a, r) {
  ...
  for (var c = 0; c < e.length; c++) e[c] = [].concat(e[c].concat(l));   // O(现有行数 × 现有列数)
  for (var u = 0; u < t; u++) e.push([].concat(o));
```

`celldata` 按行递增排列 → **每新增一行就触发一次全表复制** → 总代价 ≈ O(行数² × 列数)。

**实测验证（真实 Chromium，同一份数据、同样配置）**：

| 行数 | 路线 A：只传 `celldata`（现状） | 路线 C：同时传 `data`（二维数组） | 提升 |
|---|---|---|---|
| 5,000 | 3,513 ms | **93 ms** | 38× |
| 10,000 | 14,649 ms | **134 ms** | 109× |
| 20,000 | 62,462 ms | **264 ms** | 237× |
| **44,579** | **> 180,000 ms（卡死）** | **545 ms** | **> 330×** |

佐证：`celldata` 为空、1 万行 → **19 ms**（无 celldata 则循环不执行，行数本身不花钱）；CPU Profile 显示热点函数 `initialjfFile`（内含 `buildGridData` 调用）自耗时占 **75.8%**。
路线 C 耗时随行数**线性**增长，且 `createMs` 之外无需额外复制。

### 根因 2：`XLSX.read` 解析了全部 7 个工作表

`excelIO.readExcelFile` 只使用 `workbook.SheetNames[0]`，但 `XLSX.read` 默认解析**整本工作簿**。该文件第 3 个表「应收已收未收」有 156 万单元格，纯属白读。

| 参数 | 耗时 |
|---|---|
| 当前 `{ cellNF: true }`（解析全部 7 表） | 15,636 ms |
| `{ cellNF: true, sheets: 0 }` | **2,037–3,562 ms** |

**省 12–13.5 秒（−77%）**。注意 `cellNF` 必须保留（否则 `cell.z` 丢失、日期归一失效），去掉它只省 69 ms、无意义。

### 根因 3：校验调度"调度开销远大于有效计算"

`validationScheduler` 固定 `batchSize = 50` → 44,575 行产生 **892 个批次**；每批都调用 `updateStatsNow()`，而它每次都执行**全表 18 列扫描**的 `getFilledRowCount()`（单次 9 ms × 892 = **8.0 秒**）。批次切换在浏览器中受 4 ms 最小间隔限制 → **再 ≥3.6 秒**。

**真实有效计算只有 685 ms**（`validateRow` 全表 280 ms + `validateConditionalRow` 30 ms + `validateAllCrossRow` 377 ms）。即 **17.4 秒里有 96% 是纯开销**。

## 四、优化方案

### 【P0-1】建表改走 `data` 二维数组（收益最大）

| 项 | 内容 |
|---|---|
| 问题 | `buildGridData` 的 O(行数²) 复制 |
| 改法 | `initLuckysheet` 中**不再传 `celldata`**，改为构造并传入 `data`（二维 flowdata 数组，下标 = 行，元素 = `{v,m,ct,...}` 或 `null`）；`importData` 直接把 remap 后的数据写进二维数组，省掉 42.5 万个中间对象的构造 |
| 涉及 | `components/FinanceTableEditor.vue`（`initLuckysheet` / `importData`）、`components/TableEditor.vue`（同上，房产模块同步受益） |
| 预期 | 建表 **>180 s → ~0.55 s**（44,579 行实测） |
| 风险 | 中等。Luckysheet 不再维护 `sheet.celldata`，而 `handleBulkEdit` / `handleBulkDelete` 依赖它做双写同步 → **需一并回归**（见第六节） |

### 【P0-2】只解析第一个工作表

| 项 | 内容 |
|---|---|
| 改法 | `XLSX.read(data, { type: 'array', cellNF: true, sheets: 0 })` |
| 涉及 | `utils/excelIO.ts` 一行 |
| 预期 | **15.6 s → 2.0–3.6 s** |
| 风险 | 极低。工具本来就只读 `SheetNames[0]`，行为完全不变 |

### 【P0-3】校验调度改为"时间预算分批" + 统计增量

| 项 | 内容 |
|---|---|
| 改法 | ① 调度器由"固定 50 行/批"改为**按时间预算**（如每批跑满 25 ms 再让出主线程），批次数从 892 降到 ~30；② `updateStatsNow` 去掉每批全表重算：错误/警告数按增量累加，`filledRows` 改为**增量维护**（行由空→非空时 +1），或仅在批次结束、进度更新节流（如每 250 ms）时算一次 |
| 涉及 | `engine/validationScheduler.ts`、`engine/finance/validationStore.ts`、`engine/validationStore.ts`（房产平行副本）、`engine/finance/simpleValidator.ts` + `engine/simpleValidator.ts`（提供增量统计） |
| 预期 | **17.4 s → 1.2–2.0 s** |
| 风险 | 低。进度条语义需保持（`current/total` 改为按已处理行数上报） |

### 【P1-1】`buildDateMap` 只遍历实际存在的单元格

| 项 | 内容 |
|---|---|
| 改法 | 由「双重循环 44,579×27 并每次 `encode_cell()` 分配地址字符串」改为「遍历 `Object.keys(sheet)`（仅 425,718 个真实单元格）」 |
| 涉及 | `utils/excelIO.ts` |
| 实测 | **897 ms → 514 ms** |
| 风险 | 极低（已有单测覆盖日期归一行为） |

### 【P1-2】导入链路的对象分配瘦身

`importData` 改为直接构造二维数组后，省去 425,668 个 `CellData` 对象的构造与后续 GC（原 115 ms + 内存）。可与 P0-1 合并完成。

### 【P2】房产模块与应收模块的平行副本对齐（顺手补齐）

| 项 | 内容 |
|---|---|
| 问题 | `engine/validationStore.ts`（房产）的 `handleBulkEdit` 仍用 `celldata.findIndex` 逐格查找（O(n²)），而应收版已改为 `celldataIndex` Map 的 O(1) 查找 |
| 改法 | 把应收版的索引化方案同步到房产版 |
| 涉及 | `engine/validationStore.ts` |
| 预期 | 房产模块大批量编辑不再随行数劣化 |

## 六、改走 `data` 对 `sheet.celldata` 影响（已实测确认）

### 6.1 前提纠正：Luckysheet 从来不"维护" `celldata`

真实 Chromium 实测（**路线 A，即现状**）：

| 步骤 | `flowdata`（`sheet.data`） | `sheet.celldata` |
|---|---|---|
| `create` 后 | 304 行 | 1501 条 |
| `setCellValue(5,1,"EDITED")` 后 | **(5,1) = "EDITED"** ✅ 已更新 | **(5,1) 仍 = "v1_1"** ❌ 未更新 |

⇒ **`celldata` 从 `create` 那一刻起就是只读快照，Luckysheet 在任何编辑后都不回写它。**
所以现行代码里的"flowdata + celldata 双写"**并不是在配合 Luckysheet，而是在维护一份 Luckysheet 自己都不读的副本**。
"改走 `data` 后不再维护 celldata"的准确含义是：**`sheet.celldata` 这个键干脆不再出现**。

### 6.2 逐处影响清单

| # | 代码位置 | 路线 C 下的实际行为（已实测） | 处置 |
|---|---|---|---|
| 1 | `initLuckysheet(extraCelldata?)` | 改动本体：改为构造二维数组传给 `data` | **必须改** |
| 2 | `importData`（两个编辑器） | 改为直接产出二维数组，省掉 42.5 万个 `CellData` 对象 | **必须改** |
| 3 | `checkDraft` 草稿恢复（两个编辑器） | `draft.celldata.filter(...)` → `initLuckysheet(dataCells)`；若只改 1/2 而不改这里，恢复草稿会**又走回 O(n²) 路径** | **必须改（最易漏）** |
| 4 | `autoSave.getCurrentCelldata()` | 从 `flowdata` 反推（`getSheetData()`），**不读 `sheet.celldata`** | ✅ 无影响 |
| 5 | `handleBulkEdit` 的 celldata 双写 | `sheet?.celldata \|\| []` 得到**临时空数组**，`push` 进去的内容直接丢弃（实测 `push` 后长度 1、无异常） | ✅ 无功能影响；**建议删除该段**（从"维护废弃副本"变成"空操作"） |
| 6 | `handleBulkDelete` 的 celldata 清理 | `Array.isArray(sheet.celldata)` = **false**（实测）→ `if (Array.isArray(celldata) && ...)` 整段跳过 | ✅ 行为安全；**建议一并跳过 `cellsToDelete` 的构建**（否则仍白建 40k×18 = 72 万个字符串） |
| 7 | `engine/validationStore.ts`（房产）的 `celldata.findIndex` | celldata 空 → 循环体不执行，**O(n²) 自然消失** | ✅ 该 P2 项可随之取消 |
| 8 | 导出 `exportExcel` | 读 `flowdata` + `getAllSheets()[0].config.merge`；实测 `merge` 保留 `["0_0"]` | ✅ 无影响 |
| 9 | `types.CellData` / `AutoSaveData.celldata` | 仅类型与草稿 JSON 结构，可保留不变 | ✅ 无影响 |
| 10 | Luckysheet 内部 | 真正读取 `sheet.celldata` 的只有**多表懒加载**路径（`loadSheetUrl` / `checkLoadSheetIndex`），本项目未启用；其余全是 `iscelldata()`（区域格式判断）与透视表自身的 `celldata` | ✅ 无影响 |

### 6.4 落地建议：把改动收在 `initLuckysheet` 内部

`initLuckysheet(cells: CellData[])` **保持对外签名不变**，内部一次性转成二维数组再传 `data`：
- 好处：`importData` / `checkDraft` / 未来任何调用方都不用改，风险面最小
- 代价：仍构造 42.5 万个对象（约 115 ms）——可接受
- 若要追求极致，可让 `importData` 直接产出二维数组并让 `initLuckysheet` 兼容两种入参

### 6.5 其余两项核查

| # | 点 | 结论 |

| 7 | `sheets: 0` 与工作表顺序 | 用户文件数据必须在**第一个**工作表；当前代码本就是这个前提，行为不变——建议 UI 加提示 |
| 8 | 进度条语义 | 时间预算分批后，`progress.current` 需按"已处理行数"上报，不能按批次数 |
