## 逐项复核结论

### P0-1　`wheel` 监听器解绑缺 `capture` → 内存泄漏　✅ **真实缺陷**

**涉及模块**　`TableEditor.vue:999-1076`、`FinanceTableEditor.vue:1103-1152`

**现有实现**
```ts
// 注册（:1075）
document.addEventListener('wheel', shiftScrollHandler, { capture: true, passive: false })

// 解绑（:1016 onBeforeUnmount / :1051 setupShiftScroll 内重入防护）
document.removeEventListener('wheel', shiftScrollHandler)   // ← 缺 capture
```

**判定依据**
1. **DOM 规范**：`removeEventListener` 的 `capture` 必须与注册时一致，否则不移除。已用 Node 模拟验证：缺 `capture` 解绑后监听器数仍为 1；补上 `{capture:true}` 后归零。
2. **无任何补偿机制**：全项目无 `AbortController`、无 `luckysheet.destroy()` 清理该监听器（`destroy()` 仅在 `importData` 内被调用，而 `destroy` 不解绑自定义 document 监听器）。
3. **可累积**：`onBeforeUnmount` 在 `App.vue` 切视图时反复触发，每进出一���编辑器泄漏一个 handler。

**影响范围**
- 泄漏累积：进出编辑器 N 次 → N 个 handler 常驻
- **行为后果**：每次 Shift+滚轮，N 个 handler 各自执行 `scrollbarX.scrollLeft += e.deltaY`（:1072）→ 横向滚动速度为正常的 N 倍
- 两个编辑器**各有一份**，且 `setupShiftScroll` 内的"重入防护"（:1050-1052）因解绑无效而形同虚设

**误报风险**　低。规范行为明确，已实测验证。

**性质**　真实缺陷，但属**渐进式 UX 劣化**（非数据损坏、非功能失效），实际危害需累积多次进出才显现。

### P0-2　`column: 30` 与 32 列定义不一致　❌ **误报（feature 残留，非缺陷）**

**涉及模块**　`TableEditor.vue:616`、`types/index.ts:45-78`

**表面证据**
- `HEADER_COLUMNS` 有 **32** 项（`colIndex: 0..31`）
- `luckysheet.create` 传 `column: 30`
- `types/index.ts:44` 注释写"30列"，`HomeView.vue:43` 标签写"30列字段"
- 而 `使用说明书.md:109` 写"32列字段"

**证伪过程（关键）**
读 `node_modules/luckysheet/dist/luckysheet.esm.js` 的 `buildGridData` 实现：

```js
buildGridData: function(e){
  var t = null==e.row ? ga.defaultrowNum : e.row,
      a = null==e.column ? ga.defaultcolumnNum : e.column,   // column 仅在此参与
      r = e.data && e.data.length>0 ? e.data : Zo([],t,a),  // ← 传了 data 就完全不用 t/a
      ...
  if(e.data && e.data.length>0)
    for(var l=0;l<r.length;l++)
      for(var i=0;i<r[0].length;i++)   // ← 列数取自 r[0].length
        Cs(l,i,r,r[l][i]);
```

**实测验证**：以真实 `HEADER_COLUMNS`（32 项）跑 `toGridData(cells, 100, 32)`，产出 `grid[0].length = 32`，表头 col30/col31 均正常写入。

**结论**　项目走的是 `data`（二维数组）建表路径，`column` 参数**被 Luckysheet 完全忽略**，实际列数由数据宽度决定 = 32。**col30/col31 可见、可编辑、可导出，不存在"列不可见"缺陷**。

**`column: 30` 的真实性质**　是"改用 `data` 建表前的历史残留"——注释 `:614` 自述"行数跟随实际数据：row 同时决定滚动条范围与网格尺寸"，说明作者已同步改了 `row` 却漏改 `column`。

**真实存在的问题降级为**
| 项 | 级别 | 说明 |
|---|---|---|
| `HomeView.vue:43` 标签"30列字段"与实际 32 列不符 | **P3 文案** | 用户可见的信息错误，非功能缺陷 |
| `types/index.ts:44` 注释"30列" | **P3 注释** | 同上 |
| `column: 30` 死配置 | **P2 清理项** | 无功能影响，但误导后续维护者 |

**误报风险**　~~高~~ → 实为高。**上一轮未读 Luckysheet 源码，仅凭 `column` 字面量与 `HEADER_COLUMNS.length` 比对就判定为缺陷，属推断错误。**

### P0-3　财务 `cellUpdated(r,c)` 仅 2 参导致批量编辑失效　⚠️ **部分真实（降级 P2）**

**涉及模块**　`FinanceTableEditor.vue:653-657`

**现有实现**
```ts
cellUpdated(r: number, c: number) {
  if (r < FINANCE_HEADER_ROW_COUNT) return
  handleCellUpdate(r, c, null, null)     // oldValue/newValue 恒为 null
},
```
对比房产侧（`TableEditor.vue:647-650`）签名完整：`cellUpdated(r, c, oldValue, newValue, isRefresh)`。

**判定依据**
1. `handleCellUpdate:271` 用 `newValue` 计算 `isEmptyValue` → 恒为 `true` → `operationType` 恒初始化为 `'DELETE'`（:278）
2. 逻辑上 `EDIT` 只能靠 :291 的"后到非空值纠正"翻转 —— 但 `newValue` 恒 null，**该分支永不触发**
3. `git log -S` 显示 `handleCellUpdate(r, c, null, null)` 自 `249a2a0`（2026-06-22，修复生产环境批量删除卡死）引入即为如此，**非近期回归**

**为何降级：批量编辑主路径不依赖此 hook**
`flushBatchOperation` 只是三条路径之一。真正的"大批量编辑"由 **`cellMousedown` 的快照比对**驱动（:695 `operationType === 'BATCH_EDIT'`），该路径调 `getCellValue` 读真实值，与 `cellUpdated` 的 `newValue` 无关。

**实际影响收窄为**
- 仅影响 `flushBatchOperation` 中 `isActive && operationType==='EDIT'` 这一条分支（:341）在**纯 cellUpdated 驱动**下不可达
- 但该场景（>5 次更新、>100 行、无 mousedown 快照）本身是边缘路径
- 房产侧因签名完整，行为正确 —— 两模块存在**行为不一致**，但财务模块主流程（mousedown 快照）正常

**误报风险**　中。上一轮"财务批量编辑永不触发"的表述**夸大了影响范围**。

**性质**　真实但影响被高估。建议表述为"财务侧 cellUpdated 丢失 oldValue/newValue，与房产侧行为不一致"。

### P0-4　财务导出合并单元格少一列　❌ **误报（实现完全正确）**

**涉及模块**　`FinanceTableEditor.vue:1051-1059`

**现有实现**
```ts
const startCell = ws.getCell(m.r + 1, m.c + 1)
const endCell   = ws.getCell(m.r + m.rs, m.c + m.cs)
ws.mergeCells(Number(startCell.row), Number(startCell.col),
              Number(endCell.row),  Number(endCell.col))
```

**证伪过程**
用真实 `exceljs`（项目依赖 v4.4.0）构造 4 种合并形状，写入 xlsx 后读回校验 `model.merges`：

| 场景 | Luckysheet `!merges` 输入 | 期望 | 实测 | 判定 |
|---|---|---|---|---|
| 横向 | `{r:0,c:0,rs:1,cs:4}` | `A1:D1` | `A1:D1` | ✅ |
| 纵向 | `{r:0,c:0,rs:3,cs:1}` | `A1:A3` | `A1:A3` | ✅ |
| 2×2 | `{r:0,c:0,rs:2,cs:2}` | `A1:B2` | `A1:B2` | ✅ |
| 非零起点 | `{r:1,c:2,rs:1,cs:4}` | `C2:F2` | `C2:F2` | ✅ |

**数学验证**：起点 `(m.r+1, m.c+1)` 做 0→1-based 转换；终点 `(m.r+m.rs, m.c+m.cs)` 中 `rs`/`cs` 是**跨度**而非 0-based 下标，故 `r+rs` 恰好等于终点的 1-based 行号。两者自洽。

**结论**　6 处合并全部正确，无偏移错误。**上一轮判断错误。**

**误报原因**　把 `m.r+m.rs` 当成"漏加了 1"，实际这是把 0-based 跨度转 1-based 下标的**正确**写法；错误写法会是 `m.r+m.rs+1`。

**误报风险**　~~高~~ → 实为高。这是本次复核中**最明确的一处误报**。

### P0-5　`cellUpdateBefore` 3 秒冷却阻断正常输入　⚠️ **真实但影响需修正（降级 P1）**

**涉及模块**　`TableEditor.vue:643` / `FinanceTableEditor.vue:649`（`cellUpdateBefore` 内）

**现有实现**
```ts
cellUpdateBefore(r, c, value, isRefresh) {
  if (r === 0) return false
  if (window.__isBulkDeleting) return false      // 标志位，精确
  if (window.__isBulkProcessing) return false    // 标志位，精确
  if (Date.now() - window.__lastBulkDeleteTime < 3000) return false   // 时间窗，粗糙
},
```

**判定依据**
1. **确实拦截所有写入**：读 Luckysheet 源码，`cellUpdateBefore` 在 `createHookFunction(...)` 返回 false 时执行 `return void n.cancelNormalSelected()`，**包括普通键盘输入路径**（inlineStr 分支），非仅批量路径
2. **时间窗是粗糙近似**：`__lastBulkDeleteTime` 在 `handleBulkDelete` 的 `finally` 中无条件置为 `Date.now()`（`validationStore.ts:559`），此后 **3 秒内任何写入都被拒绝**
3. **注释显示并非有意如此**：`cellUpdateBefore` 处注释为"批量操作期间阻止Luckysheet内部逐格更新"，列举的两条理由都是标志位语义；时间窗这一条**没有注释说明**，与上方两条标志位检查明显不同源 —— 更像是补丁叠加的产物

**为何从 P0 降为 P1**
- 影响窗口仅 3 秒，且需先触发一次大批量删除（>100 行）
- 用户感知为"删除后短时间内点不动"，而非数据错误
- 不涉及数据损坏或校验失效

**设计意图辨析**　作者的**意图**（防止 `cellMousedown` 二次触发批量删除）本身合理，且 `cellMousedown:660` 已有同款时间窗（那里是合理的，因为只在选区大时才走该分支）。问题在于 `cellUpdateBefore` 是**全局写入门禁**，把时间窗放在这一层是**位置选错** —— 属于实现缺陷而非有意设计。

**误报风险**　低。缺陷真实，仅严重度评估偏保守。

## 修正后的优先级建议

### 第一优先（建议本周处理）

**1. P0-1 补 `capture: true`（3 行 × 2 文件）**
```ts
// TableEditor.vue:1016 与 :1051、FinanceTableEditor.vue:1103 与 :1152
document.removeEventListener('wheel', shiftScrollHandler, { capture: true })
```
理由：改动最小、风险最低、修复后横向滚动速度立即恢复正常。

**2. P0-5 收窄时间窗的作用范围**
把 `cellUpdateBefore` 里的时间窗检查改为仅在检测到批量上下文时生效（或直接移除该行 —— 因上方两个标志位已覆盖真实批量场景），保留 `cellMousedown:660` 的时间窗不变。
理由：涉及生产可用性，但需确认移除后不会让 `249a2a0` 的卡死问题复发，**建议先在测试环境验证**。

### 第二优先（排期处理）

**3. P0-3 统一财务侧 hook 签名**
```ts
cellUpdated(r: number, c: number, oldValue: any, newValue: any, isRefresh: boolean) {
```

理由：消除两模块行为漂移的又一个实例，为后续 `createTableEditorCore` 工厂重构铺路。

### 第三优先（随手清理）

**4. P0-2 残留清理**：`HomeView.vue:43` 标签改「32列字段」；`types/index.ts:44` 注释同步；`TableEditor.vue:616` 的 `column: 30` 删除或改为 `HEADER_COLUMNS.length`（当前无害，但会误导维护者）。

## 方法论反思

上一轮报告的 5 项 P0 有 2 项误报，**共同原因是"用项目代码的表象推断第三方库行为"**：

- 看到 `column: 30` 与 32 列定义不符 → 推断"列不可见"，**未验证 Luckysheet 在 `data` 路径下会忽略 `column`**
- 看到 `m.r + m.rs` 少一个 1 → 推断"偏移错误"，**未验证 `rs` 是跨度而非下标**

**改进建议**：对任何依赖第三方库（Luckysheet / ExcelJS / SheetJS）行为的判断，必须先读 `node_modules` 源码或跑最小实测，再下"缺陷"结论。项目已有 `smartform-engine-verify` 技能（esbuild 打包 + Node 断言），这类验证可常态化。
