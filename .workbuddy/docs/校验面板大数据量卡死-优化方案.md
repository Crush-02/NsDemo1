# 校验面板大数据量卡死 — 分析与优化方案

> 问题：导入 44,562 行后，打开校验面板抽屉 → 浏览器卡死
> 截图证据：警告抽屉显示 **19,233 条**，当前渲染条目"第 5 行 / 第 6 行 / …"
> 状态：**待确认**（仅方案，未编码）
> 日期：2026-10-12
> 关联：`.workbuddy/docs/smartform-dev-kit-代码检阅分析报告.md` P1-8

---

## 一、根因分析

### 1.1 先排除一个误判：计算不是瓶颈

实测（19,283 条 `results`，与真实结构一致）：

| 环节 | 实测耗时 |
|---|---|
| `getAllCellErrors()` 全量遍历 | **10.1 ms** |
| `.filter(severity !== 'CRITICAL')` | 9.0 ms |
| `groupByRow()` 分组排序 | **10.1 ms** |

**三个环节合计约 30 ms** —— 这在浏览器里是一帧的量级，**不可能是卡死的根因**。

> 这条很重要：如果按"数据量大 → JS 计算慢"去优化（比如做增量统计、缓存分组结果），方向就错了。
> 之前的性能优化方案里，17.4s 里 96% 是开销 —— 那是**校验调度**问题，与**面板渲染**是两条完全不同的链路。

### 1.2 真正的瓶颈：一次性创建 13.7 万个 DOM 节点

警告抽屉展开时，Vue 需要一次性创建：

| 节点类型 | 数量 |
|---|---|
| `div.error-group`（行分组容器） | 10,685 |
| `div.group-header`（"第 N 行"标题） | 10,685 |
| `div.error-item`（条目） | **19,233** |
| `span.error-severity` | 19,233 |
| `span.error-col` | 19,233 |
| `span.error-msg` | 19,233 |
| `span.error-more`（条件渲染） | 视情况 |
| **合计** | **≈ 136,768** |

**每个 `error-item` 上还有一个内联 `@click="navigateToCell(...)"`** —— 即 **19,233 个独立的事件监听器**。

浏览器主线程需要：
1. 创建 13.7 万个 DOM 节点（每个都要走完整的创建流程）
2. 挂载 1.9 万个事件监听器
3. **一次性计算 13.7 万个盒模型的布局** —— 这是最贵的一步
4. 绘制

### 1.3 放大因素：`word-break: break-all`

```css
.error-msg { flex: 1; color: #606266; word-break: break-all; }   /* :503 */
```

截图里的消息是 **"支付方式必须为：现金、银行转账、微信、支付宝、对公汇出、其它"**（约 30 个中文字符）。

- `word-break: break-all` 允许在**任意字符间断行**（中文场景下毫无必要，中文本身就能自然换行）
- 面板宽度约 360px，每条消息换行 **3~4 行**
- 19,233 条 × 4 行 × 20px 行高 ≈ **1,539 px** 内容高度（面板可视区仅约 600px，需要滚动）
- `break-all` 让浏览器无法用快速的 CJK 断行路径，逐字符测宽 → **布局耗时再放大数倍**

### 1.4 放大因素：`getAllCellErrors()` 被重复调用 2 次

```ts
const errorGroups   = computed(() => groupByRow(getAllCellErrors().filter(...)))  // :225
const warningGroups = computed(() => groupByRow(getAllCellErrors().filter(...)))  // :231
```

两个 computed **各自独立调用** `getAllCellErrors()`，各自遍历 19,283 条 Map。加上 `counts`（:175）的 3 次 `forEach`，一次展开共发生 **5 次全量遍历**。

虽然每次仅 10ms（合计约 50ms），但这是**纯浪费** —— 同一个函数被算了两遍，结果只用了过滤后的不同子集。

### 1.5 放大因素：`v-for` 的 key 在渲染期做字符串拼接

```html
:key="`${err.row}-${err.col}-${err.messages[0]}`"    <!-- :68 -->
```

内层 `v-for` 的 key 需要**读取 `err.messages[0]`** 并做模板字符串拼接，19,233 次。更关键的是：分组后同一行有约 1.8 条，key 的唯一性完全依赖 `col + messages[0]` 组合 —— 一旦同一单元格有多条相同消息，就会 **key 重复**，触发 Vue 的 patch 异常（视觉上表现为复用错乱）。

### 1.6 次要因素：`transition` 与 `animation`

```css
.slide-enter-active { transition: transform 0.25s ease; }   /* :549 */
.drawer-body { animation: drawer-expand 0.16s ease-out; }   /* :448 */
```

抽屉展开同时触发 `<transition name="slide">` 的位移过渡 + `.drawer-body` 的透明度动画。动画期间浏览器需要**逐帧重新合成**，若此时刚创建了 13.7 万节点，首帧成本极高。

### 1.7 根因归纳

| 层级 | 问题 | 权重 |
|---|---|---|
| **主因** | 无虚拟滚动 / 无分页，一次性创建 13.7 万 DOM 节点 + 1.9 万监听器 | 🔴 决定性 |
| **放大 1** | `word-break: break-all` 逐字符断行，布局耗时倍增 | 🔴 严重 |
| **放大 2** | `getAllCellErrors()` 重复全量遍历 2 次 | 🟡 中等 |
| **放大 3** | key 拼接 `messages[0]`，有重复风险 | 🟡 中等 |
| **放大 4** | 展开动画与巨量创建同帧 | 🟡 中等 |
| 背景 | 面板 100% 与表格区同时存在，Luckysheet 本身已占大量内存 | 🟡 叠加 |

> **重要前提**：本轮三抽屉改造（commit `1e7a450`）让"默认收起"生效了 —— 打开面板本身是快的（`counts` 只累加不建对象）。
> **卡死发生在用户点击"警告"抽屉展开的瞬间**，而不是打开面板的瞬间。这个区分很重要，决定了修复要落在"展开后的渲染"而非"面板挂载"。

## 三、优化方案

### 【方案 A】分片渲染 + 滚动加载（推荐 · 短期 + 中期）

**思路**：抽屉展开时**只渲染可见区域附近**的条目，滚动到底部时加载下一批。

| 项 | 内容 |
|---|---|
| **改动点** | 两个 Panel 的 `drawer-body` |
| **实现** | ① 加 `renderLimit` ref（初始 100）<br>② `v-for="group in warningGroups.slice(0, renderLimit)"`<br>③ `.drawer-body` 加 `@scroll` 监听，`scrollTop + clientHeight > scrollHeight - 200` 时 `renderLimit += 100`<br>④ 抽屉收起时 `renderLimit` 重置为 100 |
| **DOM 规模** | 13.7 万 → **约 600~1000 个节点**（≈ **1/150**） |
| **改动量** | 每个面板约 30 行 |
| **优点** | 不引入新依赖；实现直观；首屏极快 |
| **缺点** | 仍是"越来越慢"模式 —— 滚到 19,233 条全加载完，仍会卡 |
| **风险** | 低。需注意 `slice` 的数组拷贝（19,233 条 slice 开销 <1ms，可接受） |

**变体 A2（更优）**：配合**分组键 + 二分查找**，只渲染滚动位置附近的分组，而非从头 slice。复杂度中等，但彻底避免长列表累积。

---

### 【方案 B】虚拟滚动（推荐 · 长期正解）

**思路**：只渲染视口内的行，用上下占位块撑出总高度。

| 项 | 内容 |
|---|---|
| **改动点** | 同方案 A |
| **实现** | ① 计算 `itemHeight`（固定行高时可精确）<br>② `startIndex = floor(scrollTop / itemHeight)`<br>③ 渲染 `groups.slice(startIndex, startIndex + visibleCount + buffer)`<br>④ 容器上下加 `paddingTop/paddingBottom` 或两个空的 `div` 占位 |
| **DOM 规模** | **恒定约 30~50 个节点**，与总量无关 |
| **改动量** | 每个面板约 60~80 行 |
| **优点** | 性能天花板最高，10 万条也稳 |
| **缺点** | ① 行高不固定时（消息长短不一）测量复杂<br>② `group-header` 与 `error-item` 高度不同，虚拟化粒度需按组计算<br>③ 手写约 80 行，测试成本高 |

**依赖选项**：
- `vue-virtual-scroller` / `@tanstack/vue-virtual` —— 省事但引入依赖（当前 bundle 已 2.49MB / gzip 785KB，**不建议再加**）
- **推荐手写**：本项目 UI 简单（分组 + 列表），手写可控且零依赖

---

### 【方案 C】分页（低成本兜底 · 短期规避）

**思路**：抽屉底部加分页器，每页 50 条。

| 项 | 内容 |
|---|---|
| **DOM 规模** | 13.7 万 → **约 300 个节点/页** |
| **改动量** | 每个面板约 40 行（模板 + 分页状态 + 按钮） |
| **优点** | 实现最简单，行为可预期，用户可跳页 |
| **缺点** | 19,233 条 / 50 = **385 页**，翻页体验差；定位具体某条错误麻烦 |
| **适用** | 快速止血，不适合作为终态 |

---

### 【方案 D】聚合去重展示（推荐 · 收益极高）

**思路**：19,233 条警告里，**绝大部分是同一条消息重复**（截图可见全是"支付方式必须为：…"）。

改为**按「消息 + 列」聚合**：

```
⚠ 支付方式必须为：现金、银行转账、微信、支付宝、对公汇出、其它
  共 12,846 处  ·  列 H  ·  行 5, 6, 7, ... （展开全部）
```

| 项 | 内容 |
|---|---|
| **DOM 规模** | 13.7 万 → **约 20~50 个节点**（聚合后通常只有几条） |
| **改动量** | 每个面板约 50 行（新增 `groupByMessage` computed） |
| **优点** | ① 性能提升**数量级**；② 用户体验反而更好 —— 一眼看清"哪些列有哪类问题"；③ 与业务场景高度契合（批量导入的共性问题天然成批出现） |
| **缺点** | ① 丢失逐条点击定位的直观性（需二级展开）<br>② 与现有交互习惯不同，需用户适应 |
| **风险** | 中低。聚合逻辑本身简单，但交互需重新设计 |

> **这是本方案中性价比最高的一项**：19233 → 几十，收益远超 A/B/C，且**天然贴合"批量数据共性问题"的场景**。

---

### 【方案 E】样式与计算优化（必做 · 配套）

| 子项 | 改动 | 预期 |
|---|---|---|
| **E1 去掉 `word-break: break-all`** | `.error-msg` 改为默认 CJK 断行（中文场景下等效，`overflow-wrap: break-word` 兜底长英文） | 布局耗时**数倍**下降；改动 1 行 |
| **E2 `getAllCellErrors()` 单次调用** | 在 `errorGroups` / `warningGroups` 上游加一个共享 computed，一次遍历按 severity 分流 | 省 10ms + 消除重复遍历；改动约 10 行 |
| **E3 key 简化** | `:key="err.row + '-' + err.col"`（分组内 col 已唯一），不读 `messages[0]` | 消除 key 重复风险；改动 1 行 |
| **E4 展开动画错帧** | 抽屉展开时先渲染骨架、`nextTick` 后再触发动画 | 避免动画与巨量创建同帧 |

> E1 是**单行改动、零风险、收益数倍**，应当第一个做。

---

### 【方案 F】交互层规避（补充）

| 子项 | 说明 |
|---|---|
| F1 展开前提示 | 数量 > 1,000 时弹出「共 19,233 条，是否按规则聚合查看？」，默认聚合 |
| F2 搜索/筛选 | 抽屉顶部加输入框，按行号/列/消息过滤，从源头减少渲染量 |
| F3 只看错误 | 提供"仅显示 CRITICAL"开关（当前 19,233 条全是警告，往往不是用户关心的） |

> F3 尤其值得注意：**用户点开面板通常是为了看"错误"，而这里 19,233 条都是警告**。截图右下角显示"错误 0" —— 展开的这条警告列表可能并非用户真正需要的内容。

## 四、方案对比与推荐

| 方案 | 改动成本 | 风险 | 性能收益 | 适用场景 | 推荐 |
|---|---|---|---|---|---|
| **E1 去 break-all** | 1 行 | 极低 | **数倍**（布局） | 任何时候 | ⭐⭐⭐⭐⭐ **立即做** |
| **D 聚合去重** | ~50 行 ×2 | 中低 | **数量级**（19233→几十） | 共性问题为主的导入数据 | ⭐⭐⭐⭐⭐ **强烈推荐** |
| **A 分片渲染** | ~30 行 ×2 | 低 | 约 150×（首屏） | 快速止血 | ⭐⭐⭐⭐ |
| **E2 单次遍历** | ~10 行 ×2 | 低 | ~10ms | 配套 | ⭐⭐⭐⭐ |
| **F3 只看错误** | ~15 行 ×2 | 低 | 极大（用户视角） | 体验优化 | ⭐⭐⭐⭐ |
| **A2/B 虚拟滚动** | ~80 行 ×2 | 中 | **天花板最高** | 长期方案 | ⭐⭐⭐ |
| **C 分页** | ~40 行 ×2 | 低 | 约 450×（单页） | 快速止血 | ⭐⭐ |
| **F1/F2 提示与搜索** | ~25 行 ×2 | 低 | 间接 | 补充 | ⭐⭐ |

### 推荐实施顺序

**第一阶段（约 1~2 小时，立竿见影）**
1. **E1** 去掉 `word-break: break-all`
2. **E3** 简化 key
3. **F3** 加"仅显示错误"开关（截图场景下错误为 0，用户根本不需要看 19,233 条警告）

→ 预期：展开警告不再卡死（因为大多数时候用户根本不会去展开纯警告列表）

**第二阶段（约 0.5~1 天，解决本质）**
4. **D 聚合去重展示** + **E2** 单次遍历

→ 预期：19,233 条聚合为约 20~50 条，DOM 降至三位数

**第三阶段（可选，长期）**
5. **A 分片渲染**（若聚合后仍需逐条浏览）或 **B 虚拟滚动**
