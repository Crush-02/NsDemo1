> 日期：2026-10-12

## 一、为什么这个方案值得做

19,233 条警告里，**绝大部分是同一句话重复了几万次**。

我按 `engine/finance/` 的真实消息构造了 4.4 万行的典型错误分布，实测聚合结果：

```
原始条目: 20,329  →  聚合后: 37 组
DOM: ≈122,048 节点 / 20,329 监听器  →  ≈272 节点 / 37 监听器
降幅: 449×
```

聚合后的清单长这样：

| 条目数 | 列 | 消息 |
|---|---|---|
| **19,996** | 14 | 支付方式必须为：现金、银行转账、微信、支付宝、对公汇出、其它 |
| 200 | 6 | 应收金额必须为大于0的数值，最多保留2位小数 |
| 50 | 2 | 收费对象不可为空 |
| 50 | 12 | 减免分类必须为：物业费、水费、电费、车位费、公共维修费 |
| 33 | 3 | 房产简称"…"的收费科目"…"…存在重复数据（**动态文案，逐条不同**） |

**这个收敛比之所以成立，是因为批量导入的共性问题天然成批出现** —— 一列没填，就是几万条一样的错误。

### 更重要的：这不是"为了性能牺牲体验"，而是体验更好

现在的列表要求用户自己在 19,233 行里找「第 47,382 行的支付方式有问题」。聚合成一句话后：

> **支付方式必须为：现金、银行转账、微信、支付宝、对公汇出、其它**
> **共 19,996 处 · 支付方式列 · 首批行号：5, 6, 7, 8 …**

用户立刻知道「整列没填支付方式」，这才是他真正要的信息。**性能收益是副产品，认知负担下降才是主收益。**

## 二、一个必须避开的坑：不能只按 message 聚合

直觉写法是 `Map<message, CellError[]>`。**这是错的。**

我扫了全部财务规则的消息，发现有些文案**不含列名**，同一条消息会横跨多个列：

```
"缴款金额、缴款日期、支付方式三个字段需同时填写或同时为空"
  → 出现在 col 13（缴款金额）、col 15（缴款日期）、col 16（支付方式）
```

如果只按 message 聚合，这三个列的问题会混进同一组，用户点进去**不知道是哪一列**，还得自己分辨。

### 正确键：`(message, col)` 二元组

```ts
const key = `${col}||${message}`     // 用分隔符，避免列号与文案拼接产生歧义
```

这样"日期格式错误"横跨 5 个日期列时，会正确拆成 5 组。

> 顺带说明：为什么不能直接用 `results` 的 Map key（`"row-col"`）？
> 因为那是**行级**的。同一条消息散落在 2 万行上，会有 2 万个不同的 key —— 起不到聚合作用。
> 聚合必须发生在 `getAllCellErrors()` 之后，按"问题类型"重新归并。

## 三、数据结构设计

### 聚合项的类型

```ts
interface AggregatedIssue {
  /** 聚合键：列号 + 文案，保证同列同文案归为一组 */
  key: string
  /** 问题所在列（0-based，工具列索引） */
  col: number
  /** 列名（展示用，如「支付方式」） */
  colLabel: string
  /** 问题文案（组内唯一，故每组只需存一份） */
  message: string
  /** 最严重级别（与 getAllCellErrors 同口径：CRITICAL > HIGH > MEDIUM） */
  severity: Severity
  /** 该组的总条数 */
  count: number
  /** 命中行号（0-based，升序）—— 供二级展开与定位 */
  rows: number[]
}
```

### 为什么保留 `rows` 数组而不是只存 count

三个理由：

1. **二级展开要显示明细** —— 用户可能想确认"是不是所有行都有问题"
2. **定位要跳到具体单元格** —— 点某一行应该 `navigateToCell(row, col)`
3. **内存可接受** —— 19,996 个数字 ≈ 160KB（每行 4 个指向同一小整数，V8 会用 SMI 优化），相比省下的 12 万 DOM 节点完全不划算得计较

但要注意：**`rows` 在大数据量下不要做深响应式**（见第五节）。

## 四、交互设计

### 4.1 主视图（聚合态）

```
┌─────────────────────────────────────────────┐
│ ▼ 错误 (0)                                   │
├─────────────────────────────────────────────┤
│ ▼ 警告 (19,233)                              │
│                                             │
│  ⚠ 支付方式必须为：现金、银行转账、微信…        │
│    支付方式列 · 共 19,996 处                 │
│                              [展开明细 ▸]   │
│                                             │
│  ⚠ 应收金额必须为大于0的数值，最多保留2位小数   │
│    应收金额列 · 共 200 处                    │
│                              [展开明细 ▸]   │
│                                             │
│  ⚠ 收费对象不可为空                          │
│    收费对象列 · 共 50 处                     │
│                              [展开明细 ▸]   │
└─────────────────────────────────────────────┘
```

**要点**：
- 默认只渲染**聚合行**，DOM 降到三位数
- 每组按 `count` **降序排列** —— 数量最多的排最前，因为那是最该先解决的问题
- 显示列名，让用户知道问题在哪
- 显示总条数，与底部统计一致（口径不打架）

### 4.2 二级展开（明细态）

点「展开明细」后，二级列表**同样要限量渲染**：

```
│  ⚠ 支付方式必须为：现金、银行转账…             │
│    支付方式列 · 共 19,996 处                 │
│    ▾ 展开明细                                │
│      第 5 行    · [支付方式]                 │
│      第 6 行    · [支付方式]                 │
│      第 7 行    · [支付方式]                 │
│      … 前 100 条                             │
│      [继续加载更多]  [定位到第 5 行]         │
```

**这里必须再叠一层限量渲染**，否则用户一展开明细，19,996 条又会把浏览器打死 —— 问题只是被推迟了一层。

建议：二级默认只渲染前 **100 条**，滚动到底再加载下一批（这就是方案 A 分片渲染，在这里的复用）。

### 4.3 定位行为

| 操作 | 行为 |
|---|---|
| 点击聚合行本体 | 跳到**第一处**出错单元格（`rows[0]`） |
| 点击「展开明细」 | 展开该组明细（限量 100 条） |
| 点击某条明细 | 跳到该 `(row, col)` |

保留原有的 `navigateToCell`（含 `centerScrollbarSafely` 的贴边保护逻辑），不重写。

## 五、实现要点与边界处理

### 5.1 放在哪个层级

**建议放在 store 层，两个面板共用**，而不是各写一份。

```ts
// engine/finance/validationStore.ts 新增
export function getAggregatedIssues(severity: 'CRITICAL' | 'nonCRITICAL'): AggregatedIssue[]
```

理由：
1. 房产面板与财务面板是平行副本，聚合逻辑完全相同 → **抽到公共处避免第三次复制**
2. 聚合需要遍历全部 `results`，而 `state.results` 只在 store 里
3. 面板保持"只读 store"的既有约定（分层不倒置）

> 这也顺带缓解了检阅报告里指出的"组件重复度 83~98%"问题。

### 5.2 单一遍历（顺带解决 E2）

现在的 `errorGroups` 和 `warningGroups` **各自独立调 `getAllCellErrors()`**，是两次全量遍历。

改成一次遍历同时产出两个聚合结果：

```ts
// 单次遍历 results → 按 (col, message) 归并 → 一次得到 错误组 + 警告组
function aggregateOnce(): { errors: AggregatedIssue[]; warnings: AggregatedIssue[] }
```

**收益**：省 1 次全量遍历（约 10ms）+ 消除重复代码。

### 5.3 边界情况清单

| # | 边界 | 处理方式 |
|---|---|---|
| 1 | **动态文案无法聚合** | 如"房产简称"星都花园1"的收费科目…"—— 每条文案都含具体值。若照原样聚合，一组 1 条，等于没聚合。<br>**处理**：识别动态文案（正则检测插值特征），**单独归入「明细列表」区**，不进聚合视图。<br>**建议**：更彻底的做法是让规则**输出 `ruleId` + `params`**，由面板负责拼文案 —— 这样聚合键就能用 `ruleId`，动态文案也能聚合。详见 5.4 |
| 2 | **组数为 0** | 保持现有 `counts.total > 0` 判断；聚合数组为空时显示"无校验问题" |
| 3 | **某组 count = 1** | 不显示"展开明细"按钮（无意义），点击直接定位 |
| 4 | **rows 数组过大** | 19,996 个数字是安全的；但若单组超过 10 万，需评估是否改为"只存 count + 首批行号" |
| 5 | **rows 排序** | `getAllCellErrors()` 遍历 `Map` 的插入序，**不保证行号有序** → 必须显式 `.sort((a,b)=>a-b)`，否则"第 5 行、第 6 行"展示会乱序 |
| 6 | **同一格多条消息** | `getAllCellErrors()` 每格只产出 1 个 `CellError`（多条压进 `messages[]`）。聚合时**只取 `messages[0]`** 会丢信息<br>**处理**：按 `messages.join(';')` 参与键计算，保证不丢；或明确"仅展示首条 +N" |
| 7 | **重新校验后刷新** | `computed` 依赖 `state.results.size`（既有写法）。`clearPreviousStyles` 后 size 变化会触发重算。**需实测确认 Map 增删能触发响应式** |
| 8 | **聚合顺序稳定性** | 按 `count` 降序；count 相同时按 `col` 升序再按 `message` —— **保证刷新后顺序不跳动** |

### 5.4 更彻底的做法（可选，收益大但改动大）

当前每条 `ValidationResult` 只有 `message: string`，**没有 `ruleId`**。

若给 `ValidationResult` 增加 `ruleId`：

```ts
interface ValidationResult {
  severity: Severity
  message: string
  ruleId?: string      // 新增：跨行/条件规则的稳定标识
  params?: unknown     // 新增：文案插值参数
}
```

则聚合键可从「拼接文本」升级为 `ruleId + col`：
- **天然区分**动态与静态文案
- 聚合键不再依赖文案改版（改文案不会导致分组结构变化）
- 面板可自行拼文案，**i18n 友好**

**代价**：要改 `engine/types.ts` + 两个 store + 全部规则函数（约 30+ 处）。**建议放到阶段三**，本次先用 `(col, message)` 版本。

## 八、风险与取舍

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| **动态文案不聚合** | 🟡 中 | 若某批数据全是"数据重复"类错误，聚合几乎不收敛 → 需靠 5.1-① 的兜底（单列进明细区）或 5.4 的 ruleId。**必须在真实数据上验证收敛比** |
| **交互习惯变化** | 🟡 中 | 用户习惯了逐条列表。对策：保留"展开明细"，且聚合行本身可点击定位，路径不比原来长 |
| **总数守恒出错** | 🟡 中 | 一旦聚合逻辑有 bug，可能少报错误 → **必须写总数守恒断言** |
| 二次展开仍卡 | 🟢 低 | 已用限量渲染（100 条/批）兜底 |
| 内存（rows 数组） | 🟢 低 | 19,996 个数字 ≈ 160KB，可接受 |
